# Audit 结构化重构方案（Phase 1 Schema + Phase 2 因果攻击链）

- 版本：设计稿 v1（评审用，未写代码）
- 日期：2026-09-05
- 目标：Session → Chain → Call → Event 四层结构 + 因果（trigger_event_id）可解释，且**不改动系统原有功能**
- 关联现状：V1 已实现工具调用级闭环（call_id/chain_id/event_uuid/step_no、审批/执行回写、审计回放页/API）

---

## 0. 对建议的总体评价

方向正确，优先级判断与我们 V1 的地基一致。核心结论：

1. **“四层结构 + 因果边”是正确目标**；但不必把事件拆成十几张表——**security_events 仍应作为唯一的原始事件存储（append-only）**，其余表只做“薄聚合/索引”，避免重复存储与同步成本。
2. **因果（trigger_event_id）比“多几层表”更重要**——它直接回答“为什么最终 Block”。
3. 需要修正/细化 3 点：
   - 一个 Session 可能包含**多条链**（正常业务链、注入攻击链、外发链）。当前系统 chain_id 由 session_id 确定性派生 = 一个 session 一条链；Phase 2 需定义“链的切分/升级”规则，而不是简单把 session 当 chain。
   - `audit_fields`（字段级）应放 Phase 3，不在本轮做；但设计上为其预留。
   - “结果”之外要记录“因果”，意味着每个 Event 在写入时要能拿到**触发它的上游 Event 的 event_uuid**——这需要在引擎写入时序里贯穿（见 §4）。

- 所有既有 API 响应字段与 UI：不动。

## 2. 目标模型（Phase 1 落地版）

```
audit_sessions（薄聚合，可选先建）
  session_id  task_id  user_id  started_at  ended_at  status

audit_chains（薄聚合）
  chain_id  session_id  chain_type  started_at  ended_at
  final_risk  final_disposition  status(open/closed)

audit_calls（薄聚合）
  call_id  chain_id  session_id  seq_no(调用序号)  tool_name
  started_at  ended_at  decision  execution_status  parent_call_id(预留)

security_events（唯一原始事件存储，保持现有列）
  event_uuid  session_id  chain_id  call_id
  parent_event_id   ← 本调用内“上一步”事件（线性）
  trigger_event_id  ← 导致本事件的“因”事件（可跨调用，攻击链核心）
  step_no  event_type  ...(其余现有列不变)

audit_approvals（现有表，增列）
  + event_uuid（关联决策事件）
  （其余字段已够：approval_id/call_id/session_id/reviewer/action/decision/时间）

risk_escalations（新增，Phase 2 写）
  escalation_id  chain_id  call_id
  from_event_uuid  to_event_uuid  from_score  to_score  delta
  dominant_dimension  trigger_reason  decision  timestamp

audit_fields（Phase 3 预留，本轮只定结构不落库）
```

关键原则：
- **security_events 仍是“源”**；session/chain/call 三张表是**轻量摘要**（在引擎写决策行时同步 upsert），不做原始事件副本。
- 旧数据不迁移：老行 parent/trigger 为空、聚合表从新数据开始；回放页对旧 session 自动退化为“按时间排序的平铺事件”（当前已如此），不影响查看。

## 3. Schema 增量（Phase 1，全部 ALTER/CREATE IF NOT EXISTS 兼容）

### 3.1 security_events 追加两列
```sql
ALTER TABLE security_events ADD COLUMN parent_event_id  TEXT;  -- 本调用内上一步事件
ALTER TABLE security_events ADD COLUMN trigger_event_id TEXT;  -- 因果“因”事件（可跨调用）
CREATE INDEX idx_se_parent  ON security_events(parent_event_id);
CREATE INDEX idx_se_trigger ON security_events(trigger_event_id);
```

### 3.2 新增 audit_sessions / audit_chains / audit_calls（薄聚合）
```sql
CREATE TABLE IF NOT EXISTS audit_sessions (
  session_id TEXT PRIMARY KEY,
  task_id TEXT, user_id TEXT,
  started_at TEXT, ended_at TEXT,
  status TEXT DEFAULT 'open'          -- open / closed
);
CREATE TABLE IF NOT EXISTS audit_chains (
  chain_id TEXT PRIMARY KEY,
  session_id TEXT,
  chain_type TEXT DEFAULT 'session',  -- session / prompt_injection / exfil / credential / decoy ...
  started_at TEXT, ended_at TEXT,
  final_risk REAL, final_disposition TEXT,
  status TEXT DEFAULT 'open'          -- open / closed
);
CREATE TABLE IF NOT EXISTS audit_calls (
  call_id TEXT PRIMARY KEY,
  session_id TEXT, chain_id TEXT,
  seq_no INTEGER, tool_name TEXT,
  started_at TEXT, ended_at TEXT,
  decision TEXT, execution_status TEXT,
  parent_call_id TEXT                 -- 预留多调用子链
);
-- 索引
CREATE INDEX idx_ch_session ON audit_chains(session_id);
CREATE INDEX idx_calls_chain ON audit_calls(chain_id);
CREATE INDEX idx_calls_session ON audit_calls(session_id);
```

### 3.3 audit_approvals 追加 event_uuid 列
```sql
ALTER TABLE audit_approvals ADD COLUMN event_uuid TEXT;  -- 关联 decision 事件(step=90)
```

### 3.4 risk_escalations（Phase 2 落地）
```sql
CREATE TABLE IF NOT EXISTS risk_escalations (
  escalation_id INTEGER PRIMARY KEY AUTOINCREMENT,
  chain_id TEXT, call_id TEXT,
  from_event_uuid TEXT, to_event_uuid TEXT,
  from_score REAL, to_score REAL, delta REAL,
  dominant_dimension TEXT, trigger_reason TEXT,
  decision TEXT, timestamp TEXT
);
CREATE INDEX idx_esc_chain ON risk_escalations(chain_id);
```

> audit_fields 本轮不建（字段级属 Phase 3）；若想占位可建空表，但建议不建，避免“为拆而拆”。

## 4. 写入时序设计（谁在什么时候写什么）

单写入口仍是 `SecurityLogger`（引擎进程），SOC 只读（审批写库是唯一例外，走 resolve_approval）。

### 4.1 事件写入（log_check）
- `open_call(session_id, plugin_tool_call_id)`：
  - upsert `audit_sessions`（started_at 取首事件时间，status=open）；
  - upsert 当前 `audit_chains`（chain 规则见 §5）；
  - insert `audit_calls`（started_at）。
- 每次 `log_check`：先 `event_uuid = new_event_uuid()`，再填：
  - `parent_event_id` = 本 call 内上一条已写事件的 uuid（logger 内部按 call 维护一个“上一步”指针）；
  - `trigger_event_id` = 按“因果规则表”（§6）找到的因事件 uuid（可能在上一 call）；
- 决策行（step=90）写入后：
  - update `audit_calls`（decision/execution_status 初始值/ended_at）；
  - update `audit_chains`（final_risk/final_disposition/status；如需 close 由外部结束信号决定，见 §8 决策点）；
  - 写 `risk_escalations`（当本决策风险相对“本链上一个决策/风险锚点”上升且 delta≥阈值，或 disposition 升级）。

### 4.2 审批/执行（resolve_approval / log_execution_outcome）
- 追加 approval_outcome / execution_outcome 事件行（已实现）；
- 回填该 call 的 event_uuid 到 audit_approvals（新增列）；
- update audit_calls.execution_status → 终态。

### 4.3 回读
- `/audit/chains/{session_id}`（已有，保持）返回平铺事件；
- 新增组装函数（不改旧 API）：按 chain→call→event 组装树，并附 chain 摘要 + 因果边列表 + 升级记录，供回放页“链图”渲染。

## 5. 关于 Chain 的定义（需明确的一个关键规则）

### 现状问题
chain_id = md5(session) → 一个 session 一条链；无法表达“同一 session 里，正常任务之后出现一次攻击”的多链。

### 建议的 V1.5 规则（简单、可解释、不破坏现状）
- 默认：每个 session 首事件自动开 `chain_type='session'` 的“会话链”（chain_id 规则沿用，向后兼容，旧链路查询不变）。
- 当出现**新的高优先级风险锚点**（如 input 命中 prompt_injection、首次 CRITICAL 资产访问、DPT 泄漏、诱饵触发）且当前链 final_disposition 尚未 block/kill 时：**标记该 call 为“攻击子链起点”**，但不强制新建 chain_id（避免复杂）；
  - 折中：在 audit_chains 用 `chain_type` 字段记录“本 session 链当前聚焦的攻击类型”，由最新决策更新（如 `session→exfil`）；
  - 因果用 trigger_event_id 表达（不依赖拆链），UI 按“升级事件序列”展示攻击链。
- 是否真正拆成多条 chain 记录，作为 §8 决策点（建议竞赛阶段不拆，用 chain_type + trigger 表达，最稳）。

> 一句话：**链条“分段”交给 trigger_event_id 与 chain_type，不靠物理拆表**——复杂度最低且不破坏现有查询。

## 6. Phase 2：结构化攻击链（因果规则表）

### 6.1 语义
用 `trigger_event_id` 把“为什么最终 Block”串成一条有向因果链，例如：
```
event_101 prompt_injection(input)          (trigger=NULL, source=user/document)
   ↓ trigger
event_108 behavior_chain HIGH_ASSET_ACCESS (trigger=event_101? 由 input_context 关联)
   ↓ trigger
event_113 data_exfiltration/behavior_chain (trigger=event_108 或上一步 asset 事件)
   ↓ trigger
event_114 decision BLOCK                   (trigger=event_113)
```

### 6.2 因果规则表（引擎内实现，规则化、可测）
| 当前事件 | trigger 来源 |
|---|---|
| asset_resolved | 最近一次 input/asset 锚点（若 input_risk_store 有记录则为对应 input 事件） |
| data_classified | 同 call 的 asset_resolved 或 None |
| behavior_chain(决策行) | 本 call 内最近一个高信号子事件（virtual_hit/asset/decoy） |
| decoy_virtual_hit / decoy 类 | 本 call asset_resolved |
| data_provenance_injected | 产生该 token 的 route/读取事件 |
| data_provenance_leak_detected | 注入该 token 的事件（跨 call！） |
| permission_violation / review | 本 call 行为/资产锚点 |
| approval_outcome / execution_outcome | 对应决策事件（step=90 行） |
| decision(block/kill) | 触发升级的“因”事件（行为信号/DPT 命中/诱饵） |

实现要点：
- logger 在 session 级维护“**最近风险锚点**（event_uuid + 类型）”；
- 跨 call 的因（如 DPT 注入 → 泄漏、read → upload）通过锚点指针实现；
- 规则写成可单测的映射函数，先覆盖 Golden Path 5 种链：注入→敏感访问、敏感访问→外发、凭证访问→阻断、诱饵→阻断、DPT 泄漏→阻断。

### 6.3 risk_escalations 触发条件
- 同链内相邻两次决策行风险上升（to>from）或 disposition 升级（allow→review→block/kill）；
- dominant_dimension = 五维中贡献最大者（from details.dimensions）；
- 每条升级 = 一行，可回答“风险从 0.51 → 0.85 是哪一步、由哪个维度推动”。

- 现回放页（session→call→step 表）保留；
- 新增“因果链视图”：

  - 显示每次 risk_escalations：`from 0.51(HIGH) → to 0.85(CRITICAL) delta=+0.34 dominant=R_decoy/R_behavior reason=...`；
  - Block/Deny 终点高亮，并显示“因链”回溯（trigger_event_id 反向遍历）。

## 8. 需要你拍板的 4 个决策点

1. **是否真正拆多条 chain**：建议竞赛阶段**不拆物理链**（chain_type + trigger 表达），保持 session=链基线；如坚持拆，需定义“链结束”信号（风险解除？新 session？超时？）。
2. **audit_sessions/audit_calls 薄聚合表本轮是否建**：建议**建**（数据量小、查询友好、给 task_id/user_id 留位）；若求最小，可只用 audit_chains + 现有事件列，聚合查询用 SQL。
3. **字段级 audit_fields**：确认放 Phase 3（不建表），本轮只预留设计。
4. **chain 结束时机**：真实 OpenClaw 无“session end”hook，建议 ended_at 采用“下一链首事件时间”或由新端点（如 /audit/session/close）由 Agent 收尾调用（如可行）；否则保持 open 并在聚合查询里动态计算。

## 9. 实施顺序（不破坏现有功能）

| 步骤 | 内容 | 兼容性 |
|---|---|---|
| S1 | security_events 加 parent_event_id/trigger_event_id + 索引；audit_approvals 加 event_uuid | ALTER 追加，旧行 NULL |
| S2 | 新增 audit_sessions/audit_chains/audit_calls/risk_escalations 表 | CREATE IF NOT EXISTS |
| S3 | SecurityLogger：open_call/决策/审批/执行时同步写聚合与升级记录；维护“上一步/风险锚点”指针 | 纯增量；log_check 签名向后兼容 |
| S4 | 因果规则映射函数 + 单测（先覆盖 Golden Path 5 链） | 新代码，不改旧逻辑 |
| S5 | 组装查询/API：/audit/session/{sid}/tree、/audit/chain/{cid}/escalations（旧 API 不动） | 新增 |
| S6 | 回放页“因果链视图” | UI 新增区块 |
| S7 | 全量 pytest（现 159 项）+ V1 闭环测试保持全绿 | 验证不破坏 |

验收指标（新增，不改旧断言）：
- 一次 Golden Path 后：1 session → N call → 每条 call 事件数>0，所有新事件有 event_uuid/parent 或 trigger；
- 因果链可回答“为什么 block”：trigger 反向可达 decision 事件；
- risk_escalations 至少 1 行且 delta=to-from；
- 旧 API/旧页面/旧测试不受影响。
