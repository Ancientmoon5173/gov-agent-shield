## 1. 现状总览：审计是“双层”结构

- `src/audit_logger/logger.py`（`AuditLogger` → `audit.db` / `audit_events` 表）
- `src/audit_logger/reporter.py`（`AuditReporter`）
- 全仓 grep 未发现任何 src / samples / tests / plugin 引用它，属于早期版本遗留，被 `SecurityLogger` 取代，但未删除。

### 1.2 现行审计模块（唯一写入方）

- `src/security/security_logger.py`：`SecurityLogger` → SQLite `data/audit_logs/security_events.db`，单宽表 `security_events`（16 列），带旧库 `ALTER TABLE` 兼容升级。
- 唯一写入来源：`src/security/orchestrator.py` 的 `check_input / check_tool_call / check_output`。
- 对外暴露：`src/main.py` 提供 `/security/check_tool`、`/security/check_output`、`/security/events/{session_id}`、`/security/status`；OpenClaw 插件当前只调用 `check_tool`。
- Streamlit SOC（`src/ui/*`）通过 `data_provider.get_logger()` 读取同一张表。

### 1.3 security_events 表结构（现状）

`id / timestamp / session_id / check_type / input_text / tool_name / tool_params / risk_score / risk_level / disposition / details / event_type / policy_id / decision_reason / defense_stage / chain_summary`

- `details` 为 JSON 字符串，承载每步检测的丰富载荷（见 2.3）。
- **没有任何索引**（`PRAGMA index_list` 为空），631 个会话 2.1 万行全表扫描。

## 2. 已实现能力盘点

### 2.1 记录的事件类型（已有）

| check_type | event_type 示例 | 说明 |
|---|---|---|
| input | prompt_injection / data_exfiltration / input_risk | 用户输入检测 |
| asset_resolved | asset_resolved | 资产身份命中（asset 元数据入 details） |
| decoy_virtual_hit | decoy_virtual_hit | 行为观察器低权重信号 |
| decoy_event / decoy_route_triggered | tool_risk / decoy_route_triggered | 静态诱饵触碰、Shadow Decoy 路由 |
| data_provenance_leak / data_provenance_injected | data_provenance_leak_detected / data_provenance_injected | DPT 令牌命中/注入 |
| permission / permission_signal | permission_violation / tool_risk | 权限阻断、审批（review） |
| tool_call | behavior_chain / data_exfiltration / tool_risk | 工具调用综合评分与处置 |
| output | （缺省） | 输出敏感脱敏（masked） |

### 2.2 已有的“链”要素（半成品）

- `_build_chain_summary()`：从**内存** `BehaviorAnalyzer._history` 取最近 5 个工具名拼字符串（如 `read -> read`），写入 `chain_summary` 列。
- `BehaviorAnalyzer`：基于 operation（READ/EXFIL/QUERY/SYSTEM_EXEC…）的时间窗规则 + 行为信号（`HIGH_ASSET_ACCESS / CRITICAL_ASSET_ACCESS / HIGH_RISK_DATA_EXFIL_CHAIN / QUERY_DATA_EXFIL_CHAIN`），输出 `behavior_score / behavior_signal.evidence[]`。
- `InputRiskContext`：`source = user_input | document_context`，`risk_type = prompt_injection | data_poisoning | jailbreak | sensitive_instruction`；`boost()` 抬升 R_input。
- `DataProvenanceTracker`：DPT 令牌注册/注入/泄漏扫描，令牌 metadata 含 `source / copy_path / tool_name / data_class / asset_type`。
- 审批：引擎在 `disposition=review` 时把 `approval_id`、reason 写入 details；`src/permission/approval.py` 的 `ApprovalManager` 支持 approve/reject（**内存实现**）。
- 阻断：block/kill 决策携带 `policy_id / decision_reason / defense_stage`；插件侧 `requireApproval` 对 block/kill 用 deny-only 弹窗。
- 评测：`benchmark/metrics/audit_validator.py` 已实现“字段级完整性校验”（tool_call / Decoy / DPT 的必需字段），`benchmark/outputs/audit_field_report.json` 产出 `field_completeness`；`benchmark/e2e_real/outputs/final_audit_trace.json` 冻结 30 轮真实 OpenClaw 审计事件。

### 2.3 单条 tool_call 事件 details 载荷（已很丰富）

`dimensions`（五维 R_input/R_tool/R_output/R_behavior/R_decoy）、`param_findings`、`behavior`（含 signal/evidence/operation_history/asset_history）、`decoy`、`disposition`、`permission`（含 policy/R_permission）、`data`（分级 findings）、`asset`（资产元数据）、`input_context`（source/risk_type/findings）、`behavior_observer`、`decoy_route`（original/redirect/modified_params/token）、`data_provenance`、`inject_token`、`task_context`。

### 2.4 测试覆盖（当前全部通过）

`test_audit_enhancement.py`（block 事件字段、旧库 ALTER 兼容、chain_summary）、`test_behavior_chain.py`、`test_behavior_observer.py`、`test_data_provenance.py`、`test_decoy_route.py`、`test_decoy_abc_phase3.py` 等；全量 `154 passed`。

### 2.5 SOC UI 现状（审计展示弱）

- `src/ui/app.py` Dashboard：指标卡 + 最近事件平铺表 + Agent 状态。
- `01_monitoring.py`：等级/处置筛选 + 平铺表。
- `02_incidents.py`：5 个静态 Tab（全部/诱饵/越权/注入/外传）平铺表。
- `03_permissions.py`：Agent 权限卡 + 诱饵清单。
- `04_approvals.py`：待审批 approve/reject + 已处理历史表（读 `permission_checker._core.approval_manager`，内存态）。
- 没有任何：会话详情/时间线/证据链视图、details JSON 查看器、字段级钻取、风险升级可视化、审批与审计事件的关联展示。

## 3. 关键缺口分析（对照本会话目标）

### 3.1 事件链结构性缺失 —— 无法程序化还原“链路”

- `security_events` 没有 `event_uuid / chain_id / call_id / parent_event_id / step_no / trigger_event_id` 等关联字段。
- 一次工具调用会产生多行子事件（如真实库中 DEMO-B 一轮产生 id 19584 asset_resolved → 19585 decoy_virtual_hit → 19586 behavior_chain，随后 19587–19589 第二轮），这些行**只能靠 session_id + 时间排序猜测归属**，无请求级标识。
- `chain_summary` 是弱字符串：只含最近 5 个工具名、同一调用多行重复写入、子事件行（asset_resolved / decoy_virtual_hit）的 chain_summary 为空、**跨进程/服务重启丢失**（BehaviorAnalyzer._history 为纯内存，API 服务与 Streamlit Demo 各自实例不共享）。
- `approval_id` 只存在于 details，不与任何事件列外键关联。

### 3.2 字段级审计缺失 —— 无法回答“哪个字段”

- 只记录 `tool_params` 原始 JSON 整体、参数风险 findings（字符串）、输出正则命中的 type/position/matched。
- 没有“字段级实体”存储：`对象(资产/文档/数据库/知识库/记忆) → 字段名 → 字段值摘要 → 敏感度 → 读/写/外发/脱敏动作` 不可查询。
- DPT 令牌注入为整行/整条文本追加标记（`toolResultPersist` 在 content 末尾追加 tokenLine），是“内容级”而非“字段级”。
- 输出脱敏后的 `masked_output` 不回写 SQLite，无法还原“哪些字段被脱敏、脱敏前后对照”。
- 数据库查询 / 知识库检索等结构化结果没有字段映射链路（源字段 → Agent 上下文 → 外发参数）。

### 3.3 污染来源不可还原

- `InputRiskContextStore` 每个 session 只保存**最新一条**输入风险上下文（单值覆盖），无污染源对象标识（源文件/文档段落/知识库条目/记忆快照/具体字段与位置），findings 只是 detail 字符串。
- 文档/知识库/历史记忆内容检测在真实运行时**未闭环**：插件只调 `/security/check_tool`；`check_input(document_context)` 仅被测试脚本与 Mock Agent 使用（操作手册第 6 节限制 1、差距分析报告已自认）。
- 多源污染（用户输入 + 文档 + 知识库 + 记忆）不能在同一会话叠加、关联、溯源（比赛目标 1 的“多源输入风险关联分析”缺口）。

### 3.4 行为偏移不可度量/还原

- BehaviorAnalyzer 输出的是 rule-based 风险与信号，不是“相对任务上下文/正常基线”的偏移量：无 baseline 定义、无 deviation/delta 分数、evidence 只是字符串，不能定位“偏移发生在第几步、由哪次调用触发”。
- 没有会话级“正常行为基线画像”的持久化，无法回答“这次行为偏离了它应该做的任务多远”。

### 3.5 风险升级链路不可回放

- 每条事件有独立 `risk_score/risk_level`，但**没有相对前序步骤的升级/降级记录**（from_level→to_level、增量、主导维度、触发事件引用）。回放只能靠肉眼对比数值。
- 同一调用产生的多行子事件（asset_resolved 0.05 → behavior_chain 0.51 → …）风险语义不清，无法一键还原“发现→识别→升级→阻断”的阶梯。

### 3.6 审批 / 阻断结果不闭环

- 真实库中 `approved / denied / review_denied / 审批结果` 相关记录 **0 条**：人工审批的最终决定只存在于插件 console 日志与 OpenClaw 内存态，不回写 Python SQLite。
- `ApprovalManager` 纯内存；每次 `review` 决策都会新生成 approval_id，与后续“是否放行、是否执行”无关联记录。
- block/kill 的 deny-only 确认、terminate 是否落地（工具实际未执行）也没有审计记录（插件 `afterToolCall` 只 console.log）。
- 结论：比赛要求的“人工审批记录”目前仅 UI 内存可见，**不是可审计闭环**。

### 3.7 SQLite 工程问题

- 单宽表 + 大 JSON details；无索引（2.1 万行 / 631 会话全表扫描）；无 WAL、无清理策略（真实库已 21 MB）。
- 无 schema 版本管理/迁移框架（现在靠逐列 ALTER 兼容）。
- `SecurityLogger.get_summary()` 只统计 `allow/review/block/kill` 与 5 个等级，`detected/observed/masked/rerouted/injected` 不计入 → Dashboard“阻断/严重”口径与实际事件分布不一致。
- `input_text` 截断 300 字符等字段级信息丢失。
- 多进程写同一库（API 服务 / Streamlit demo / 测试）无协调，行为历史与输入上下文跨实例不共享。

### 3.8 历史文档已承诺但尚未实现

- README：AuditLogger = SQLite 审计事件记录（审计溯源目标）。
- `docs/竞赛作品打磨路线图.docx`：审计平台（P1）= 事件时间线、调用链、诱饵命中高亮、审批记录；“发现 → 识别 → 风险升级 → 隔离/阻断 → 阻止泄露”叙事。
- `benchmark/evidence/政企办公场景Demo对话操作手册.md`：第 8 轮要求展示 `document_context / knowledge_context / memory_context / asset_resolved / behavior_chain / data_provenance_injected / decoy_route_triggered / compliance_blocked` 多源输入事件链（当前多数事件类型不存在）；评测含“人工审批记录”。

## 4. 待实现功能建议清单（本会话后续落地排序）

### P0（直接支撑“四要素链路 + 审计完整性”）

1. **SQLite Schema v2 迁移（保留旧表与旧 API）**
   - `security_events` 增列：`event_uuid / chain_id / call_id / parent_event_id / step_no / trigger_event_id`；为 `session_id / chain_id / call_id` 建索引。
   - 新表：
     - `audit_chains`（chain_id、session_id、start/end、outcome/status、summary）
     - `audit_fields`（事件/对象/字段粒度：object_type、object_ref、field_name、value_preview、sensitivity、action、token）
     - `approval_events`（approval_id、session_id、call_id、tool、action、status、decided_at、decided_by、关联 event_id）
     - `risk_escalations`（chain 内 from→to step、level/score、driver_dimension、policy_id）
2. **事件链标识注入**：每次工具调用生成 `call_id/chain_id`，贯穿 orchestrator 全部 `log_check` 与返回 decision（插件可回写）。
3. **审批闭环回写**：插件将 allow-once/deny/confirm 结果 POST 回 `/audit/approval`，落库并关联 call_id/approval_id；阻断确认生成“工具未执行”的执行结果事件。
4. **字段级审计 v1**：结构化敏感读取结果/外发参数做字段提取与映射（源字段 → 上下文 → 外发命中），输出脱敏记录 masked 字段；新增 `data_flow` 事件。
5. **污染来源对象化 + 多源叠加**：`check_input` 的 context_text 扩展为 sources[]（document/kb/memory/field 级），InputRiskContext 持久化到会话；插件 `afterToolCall` 回扫工具结果形成 document_context 污染审计。
6. **行为偏移 v1**：任务上下文期望基线 vs 实际行为，输出 deviation（score/delta/evidence step 引用）入事件。
7. **风险升级结构化**：会话链相邻步骤自动计算 from→to 升级记录。
8. **UI 审计回放页**：按 session 的时间线（同 call 分组/父子缩进）、风险曲线 + 升级标记、污染源→偏移→升级→审批/阻断四段视图、字段明细钻取、审批与阻断徽章；修复 Dashboard 统计口径；新增审计查询 API。

## 5. 一句话结论

现有审计能回答“某次调用发生了什么”（单事件字段完整、评测字段完整性达标），但**不能还原“为什么发生、怎么一步步演变成最终处置”**：缺结构化事件链、缺字段粒度、缺审批/阻断结果回写、缺污染源对象化与多源叠加、缺风险升级记录；UI 也停留在平铺表格。这正是本会话要补的“字段级审计 + 完整事件链”核心内容。
